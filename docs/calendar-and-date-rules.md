# Calendar and date rules (AD/BS)

## Data source, licence and range
* Month lengths for Bikram Sambat years **1975–2100 BS** (1918-04-13 to 2044 AD) come from the `calendar_bs.csv`
  table of **nepali-datetime 1.0.8.5 (MIT licence)**, converted once to `shared/bs-calendar.json`.
* `scripts/sync-calendar-data.mjs` copies that file to `backend/apps/calendar_utils/data/` and
  `frontend/src/calendar/`. A backend test asserts the three copies are byte-identical.
* Years well beyond the current date (roughly after 2090 BS) are published projections; official calendars for
  those years may still change. If the Nepal Panchanga Nirnayak Samiti publishes a correction, update
  `shared/bs-calendar.json`, run the sync script and the tests.

## Conversion algorithm
Count days from the anchor **1975-01-01 BS = 1918-04-13 AD** using the exact month lengths. No fixed month length,
no year offset. Implemented identically in `apps/calendar_utils/bs.py` and `frontend/src/calendar/bs.ts`.

Verification:
* Backend: every day of the supported range (~46,000 days) is compared with nepali-datetime and round-tripped.
* Frontend: `bs.test.ts` checks 1,002 fixtures generated by the backend (`shared/bs-fixtures.json`) and
  round-trips every day of the range.

## Storage
* Business dates (invoice date, due date, order date, receipt date…) are `DateField` values in **AD**.
* Events with a time (posting time, audit events) are timezone-aware `DateTimeField` values (UTC in the database,
  shown in the organisation timezone, default **Asia/Kathmandu**).
* BS values are never stored as the source of truth; they are calculated from the stored AD date.
* Converting a datetime to BS directly is refused (`ad_to_bs(datetime)` raises) to avoid timezone day shifts.
  The frontend never parses business dates with `new Date("YYYY-MM-DD")` in local time; it uses UTC arithmetic.

## API contract
Every serializer with a date field returns `"<field>": "2026-04-14"` and `"<field>_bs": "2083-01-01"`.
On input a client may send either `<field>` (AD) or `<field>_bs` (BS). If both are sent they must denote the same
day. Invalid BS dates return HTTP 400 with the field error, e.g. `"2083-03 BS has 32 days; day 33 is invalid."`

## Filters
List and report endpoints accept (all optional, inclusive):

| Parameter | Meaning |
| --- | --- |
| `date_from`, `date_to` | AD dates |
| `date_from_bs`, `date_to_bs` | BS dates (converted on the server) |
| `fiscal_year` | Fiscal year id, `current` or `previous` |
| `period` | Accounting period id |
| `as_of` / `as_of_bs` | Balance reports |

Explicit dates narrow a selected fiscal year. Date fields are filtered with `>= start` and `<= end`.
Timestamp fields use `[start 00:00, end + 1 day 00:00)` in the organisation timezone.

## Display
Users choose **AD**, **BS** or **AD + BS** (top bar or My account); the organisation sets the default display and
the default input calendar. PDFs print `2083-01-01 BS (2026-04-14 AD)` in dual mode. CSV/Excel exports include
both an AD and a BS column for every date.

## Date picker
`DatePicker` accepts typed input in the active calendar (toggle **AD/BS** inside the field), validates real
month lengths, shows the other calendar under the field and in each calendar cell, and supports keyboard use:
type the date + Enter, `Alt+↓` to open the calendar, arrows/PageUp/PageDown/Home inside it, Enter to choose,
`Alt+T` for today (in the organisation timezone).
